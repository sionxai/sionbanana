# Sion Banana Image Gen

## When to use

Use this skill when the user asks in natural language for image creation, scene generation, character sheets, key visuals, image series exploration (e.g. "10개 만들어줘"), batch/parallel generation, character library use, or upscaling selected 시온바나나 results.

세로 웹툰 완성본(그림 안에 통합된 한글 말풍선 + 세로 이어붙이기)은 이 스킬이 아니라 **`sionbanana-webtoon`** 스킬을 쓴다. 이 스킬은 단일 키이미지·가로 스토리보드·레퍼런스 시트 중심이다.

유튜브 썸네일·영상 제목·설명란 등 **배포 단계 산출물**은 이 스킬이 아니라 **`sionbanana-thumbnail`** 스킬을 쓴다.

Prefer the local helper workflow over editing app code. `docs/agent-automation-workflow.md` is historical context; this `SKILL.md` is the source of truth.

## Prerequisites

- Run from the 시온바나나 project directory.
- 시온바나나 서버는 **launchd 상주**(`com.sionbanana.server` — 로그인 자동기동, kill해도 자동 재기동). 코드 변경 반영은 `npm run build && launchctl kickstart -k gui/501/com.sionbanana.server`. 앱 창은 `~/Applications/SionBanana.app`(Chrome 앱 모드), 수동 백업 런처 `SionBanana.command`. default port `3002`.
- Confirm `/api/health` (must return `"authenticated": true`) before generation.

```bash
curl -s http://localhost:3002/api/health
```

## Workflow

### Phase 1: 탐색 (병렬 batch — 권장)

Generate N attempts **in parallel** with `--batch N --concurrency C`. **기본 동시성 4는 "레퍼런스 없는" 프롬프트-only 생성 기준**이다 (실측: 4 parallel = no 429).

> 🚨 **referenceGallery/referenceSlug를 거는 컷은 `--concurrency 2` 이하로.** 레퍼런스 이미지는 `input-images per min` 조직 쿼터(4000)를 따로 소모해서, 동시성 3~4로 돌리면 다수 컷이 502 `"Rate limit reached ... on input-images per min"`으로 실패한다 (실측: 웹툰·반장선거 세션 공통). **한 세션에서 이미지를 많이 생성하면 이 분당 한도가 누적 포화**되어 `--retry`의 짧은 백오프로는 절대 안 풀린다 → 이미지 생성을 **수 분간 완전히 멈춰 window를 비운 뒤** 재개한다. (안전필터 502와 구분: rate limit은 reason에 "Rate limit reached"가 명시됨.)

> ⚠️ **서버/머신 부하가 높으면 2~3으로 낮춰라.** dev 서버는 이미지 생성 시 메모리를 크게 쓰므로, 다른 무거운 앱(다른 dev 서버 등)이 같이 떠 있거나 Load Average가 높으면 동시성 4에서 서버가 죽을 수 있다 (실측). 그럴 땐 spec의 `concurrency: 2` 또는 `--concurrency 2`로 낮춘다. 10 이상은 비권장 — 더 빠르지도 않고 ~20% rate-limit 실패가 난다.

```bash
node scripts/agent-generate.mjs \
  --prompt "이미지 프롬프트" \
  --category "moon-running" \
  --slug "attempt" \
  --batch 10 \
  --concurrency 4 \
  --retry 2
```

- 10개를 4개씩 동시 처리 → sequential 대비 약 2~4배 빠름 (10장 ~280초 vs ~500초)
- batch 완료 시 통합 index가 **자동 생성**됨 (`--category` 필요)
- slug는 자동 인덱싱: `attempt-01`, `attempt-02` ...
- `--retry N`은 429/502/503/504/timeout 같은 일시 오류만 재시도. 로그는 stderr로만 출력됨.

> ⚠️ **실측: 10개 batch에서 1~2개 rate limit/timeout 실패 가능** (예: 8/10). 100% 필요하면 `--retry 2` 또는 `--concurrency 3`으로 낮춤.

단건만 필요하면 `--batch` 생략:

```bash
node scripts/agent-generate.mjs --prompt "..." --category xxx --slug yyy
```

### Phase 1b: 스토리보드 (서로 다른 prompt 다건)

컷마다 prompt가 다른 경우 `--batch`가 아니라 jobs 배열을 사용. stdin은 JSON 객체(`{"jobs":[...]}`) 또는 배열을 받을 수 있음:

```bash
node scripts/agent-generate.mjs --concurrency 4 --retry 2 --port 3002 < storyboard-jobs.json
```

`storyboard-jobs.json` 예:

```json
[
  {
    "slug": "cut-01",
    "category": "storyboard-demo",
    "prompt": "첫 컷 prompt",
    "quality": "medium",
    "count": 1
  },
  {
    "slug": "cut-02",
    "category": "storyboard-demo",
    "prompt": "두 번째 컷 prompt",
    "referenceSlug": "cut-01"
  }
]
```

출력은 JSON 하나이며 `jobs[].ids`, `jobs[].imageUrls`, `jobs[].outputPaths`, `jobs[].manifestPath`를 포함. 같은 `category`의 성공 run이 있으면 마지막에 index가 생성됨.

### Phase 1c: 스토리보드 일괄 생성 (spec 기반)

시나리오별 키프레임은 임시 스크립트를 새로 만들지 않고, 사람이 작성하는 spec 파일 1개와 범용 CLI를 사용한다.

```bash
node scripts/storyboard.mjs jobs templates/storyboard.example.json
node scripts/storyboard.mjs run data/storyboard/<project>.spec.json --port 3002 > data/storyboard/<project>.summary.json
node scripts/storyboard.mjs organize data/storyboard/<project>.spec.json data/storyboard/<project>.summary.json
```

- **spec·summary는 루트가 아니라 `data/storyboard/<project>.spec.json` / `<project>.summary.json`에 둔다** — 루트에 쓰면 git status를 어지럽혀 세션 간 "이거 커밋해야 하나?" 혼란을 만든다 (실측: 루트에 부산물 33개 누적).
- spec은 `title`, `outDir`, `defaults`, `scenes[].cuts[]` 구조를 사용한다. 각 cut은 `slug`, `prompt`가 필수이고 `size`, `quality`, `count`, `category`는 cut 값이 없으면 `defaults`에서 채운다.
- ★ **콘티 메타(index에 자동 표시) — 시나리오 작업 시 반드시 채운다.** `organize`가 만드는 `index.html`은 단순 썸네일 갤러리가 아니라 **콘티(스토리보드 문서)**다. 아래 필드를 spec에 채우면 index에 그대로 렌더된다(안 채우면 그 줄이 비어 콘티 구실을 못 한다):
  - spec 최상위 `logline`(한 줄 줄거리) + `synopsis`(씬 흐름 문자열 배열) → index 상단 **📖 스토리라인** 블록.
  - 각 cut의 `sec`(예: `"0–4초"`) → 카드 라벨에 시간.
  - 각 cut의 `story`(상황 + **인물 액션**) → 카드 본문.
  - 각 cut의 `dialogue`(예: `"이완 원장: 말로 안 되면… 수기로"`, 여러 줄은 `\n`) → 카드에 대사(화자 자동 굵게). 대사 없는 컷은 생략.
  - 각 cut의 `camera`(예: `"미디엄 투샷 / 50mm / 슬로모 더치틸트"` = **카메라 액션·앵글·렌즈·샷타입**) → 카드에 🎬 줄.
  - 말풍선 없는 순수 키이미지라도 `dialogue`/`camera`는 **콘티 문서용 메타**이므로 채운다(이미지에 글자로 그려 넣으라는 뜻이 아니라, index 콘티에 그 컷의 대사·카메라를 명시하는 것).
- **해상도 기본값은 2K(`"size": "2k-16:9"` = `2048x1152`)로 한다.** 세로물은 `2k-9:16`, 정사각은 `2k-1:1`. 예전 `1824x1024`(1.9K)는 빠른 탐색용이며, 최종 딜리버리 스토리보드는 처음부터 2K로 생성한다. (별도 업스케일 단계 없이 바로 2K 결과를 얻기 위함.)
- 레퍼런스 이미지를 `data/images/<bucket>/<id>.png`에 두면 `/api/images/<id>`로 접근할 수 있으므로 `reference` 또는 `referenceGallery`에 직접 넣는다.
- 이전 `agent-generate` 결과처럼 `data/agent-runs/.../manifest.json`에 slug가 남아 있는 이미지는 `referenceSlug`, `referenceGallerySlugs`로 참조한다. 같은 `category` 안에서 최신 run의 첫 `/api/images/<id>`가 사용된다.
- `run`은 spec을 jobs로 평탄화하고, slug reference를 URL로 해석한 뒤 `runJobs`로 생성하고, `outDir/scene-<n>/<slug>_v1.png` 형태로 복사한 다음 `outDir/index.html`을 만든다.
- 검수 후 실패하거나 어색한 컷만 별도 spec으로 부분 재생성한다. 이후 기존 summary의 해당 slug 항목을 새 결과로 교체하거나, 같은 slug 항목이 뒤에 오도록 summary를 합친 뒤 `organize`를 다시 실행한다.
- 전경에 큰 신체부위(다리/발/손)가 들어가는 prompt는 원근 왜곡 위험이 높다. 주인공 중심 구도를 명확히 쓰고 negative prompt에 `giant oversized leg, distorted limbs, foot in foreground, extra limbs, deformed hands`를 넣는 편이 안전하다.
- 시나리오 헤더의 컷 수와 실제 컷 번호가 불일치할 수 있으니, 자동화는 문서 헤더보다 실제 cut 번호와 slug 기준으로 진행한다.
- `scenes[].n`은 **1 이상의 정수만** 허용된다 (`n=0` 거부, 실측). 프롤로그·에필로그는 scene 1(또는 마지막 scene)로 넣고 `title`을 "프롤로그 · …"로 적어 구분한다 — cut slug(`cut-0-1` 등)는 자유.

### 프레임 규격 — 화면비는 `size`가 아니라 프롬프트가 지배한다 ★중요

`size: "2k-16:9"`를 줘도 **프롬프트에 쓴 렌즈·포맷 용어가 화면비를 끌어간다.** (실측: 92컷 스토리보드에서 "아나모픽 렌즈"라고 썼더니 `size` 지정과 무관하게 전 컷이 2.35~2.39:1 시네마스코프로 나왔다 — 상하 레터박스까지 붙어서.)

1. **렌즈·포맷 용어를 룩 지시로 착각하지 마라.** `아나모픽`, `시네마스코프`, `와이드스크린 필름`, `70mm` 같은 단어는 질감 지시가 아니라 **비율 지시로 작동**한다. 16:9가 필요하면 이 단어들을 프롬프트에서 뺀다.
2. **원하는 비율을 문장으로 못 박는다.** 실측으로 통한 문구:

   > `★[프레임] 정확히 16:9 와이드스크린 비율(1.78:1). 시네마스코프나 극단적 와이드, 상하 레터박스 금지.`

   이 문구로 교체한 뒤 92컷 전부 1672×941(=1.777)로 통일됐다.
3. **눈으로 판정하지 말고 실측한다.** "와이드해 보인다"는 2.39와 1.78을 구분 못 한다.

   ```bash
   sips -g pixelWidth -g pixelHeight *.png \
     | awk '/pixelWidth/{w=$2} /pixelHeight/{printf "%.2f\n", w/$2}' | sort | uniq -c
   ```
4. 그래도 비율이 안 잡히는 컷은 후처리 크롭(`sips -c 864 1536`)을 폴백으로 쓴다. 단 `organize`가 canonical 원본을 다시 복사하므로 **크롭은 organize 이후 마지막 단계**로 한다.

### Phase 1d: 레퍼런스 시트 자동 생성

시나리오/스토리보드 작업 시, 사용자가 캐릭터·장소·오브젝트 레퍼런스 시트를 첨부하지 않은 경우 키프레임 생성 전에 먼저 생성한다. 첨부된 경우 이 단계를 건너뛴다.

**판단 기준**: 시나리오 텍스트에 연속성 바이블(인물/공간/오브젝트 비주얼 상세)이 있으나 참조 이미지 첨부가 없으면 자동 생성 대상.

> ★ **시트 ↔ 시나리오 정합성 검증 (시트 첨부 시 필수)**
> 사용자가 시트를 첨부한 경우, **키프레임 생성 전에 시트의 실제 외형과 시나리오 연속성 바이블의 외형(특히 의상·헤어·소품)이 일치하는지 반드시 대조**한다. 불일치하면(예: 바이블은 "후드집업+데님재킷"인데 시트는 "원피스") **컷 생성을 시작하기 전에 둘 중 하나로 통일**한다:
> - (A) 시나리오 바이블을 시트에 맞게 수정, 또는
> - (B) 시트를 바이블에 맞게 재생성(권장 — 서사 의도 보존).
>
> 이 단계를 건너뛰고 "프롬프트마다 의상을 글로 강제"하는 식으로 땜질하면, 의상 문구가 빠진 컷에서 시트 원본 외형이 튀어나와 **컷마다 옷이 바뀐다**(실측: 데님재킷 명시한 컷은 유지, 빠진 컷은 시트의 원피스로 회귀). 근본 해결은 시트와 시나리오를 처음부터 일치시키는 것이다. 불일치 발견 시 사용자에게 보고하고 (A)/(B)를 확인받는다.

#### 캐릭터 시트

인물마다 1장. 프롬프트 구조:

```
Character reference sheet for {인물명}. 
Left half: full-body front view and full-body back view standing on a plain light background.
Right half: 4-panel face grid (front, 3/4 left, 3/4 right, profile).
{나이, 성별, 체형, 신장 등 신체 특징}
{헤어스타일, 색상}
{의상 상세: 색상, 소재, 질감, 특이사항(찢어짐, 얼룩 등)}
{소품: 모자, 신발, 액세서리}
Hyperrealistic cinematic photography, natural cinematic side lighting, 35mm film look, NOT 3D game render or CGI, consistent identity across all views.
```

- `--slug "ref-char-{인물명}"`, `--quality high`, `--aspect "16:9"`
- ⚠️ 실사 작품의 시트에 "균일 스튜디오 조명 + 중립 회색 배경" 조합을 쓰지 마라 — 게임 에셋 턴테이블 톤이 되고 그 톤이 컷에 전이된다 (실전 교훈 #3과 동일). 위 템플릿의 시네마틱 측광 문구를 유지할 것.

#### 장소 시트

주요 공간마다 1장. 프롬프트 구조:

```
Location reference sheet for {장소명}, 4-panel grid labeled 정면/후면/좌측/우측.
{시대, 지역, 건축 양식}
{주요 구조물: 지붕, 벽, 바닥 재질}
{주변 환경: 식생, 지형, 돌담 등}
{조명 조건: 시간대, 계절, 날씨}
Hyperrealistic photography, architectural reference style.
```

- `--slug "ref-loc-{장소명}"`, `--quality high`, `--aspect "16:9"`

#### 오브젝트 시트 ★중요

서사적으로 반복 등장하는 소품(카메라, 무기, 탈것, 휴대폰, 상징 물건 등)은 **반드시 오브젝트 시트로 외형을 고정**한다. 시트 없이 `"futuristic vlog camera"`, `"미래형 카메라"` 같은 **추상 표현만 쓰면 컷마다 완전히 다른 물건**이 나온다 (실측: 같은 카메라가 짐벌캠·태블릿·고프로로 제각각 생성됨). 캐릭터를 시트로 고정하듯 핵심 소품도 똑같이 고정해야 한다.

권장 절차:
1. **구체적 실물 모델로 지정** — `"미래형 카메라"`(X) → `"compact mirrorless camera modeled on a Sony a7c, silver-and-black body, short retractable lens, flip-out LCD"`(O).
2. 그 묘사로 오브젝트 시트 1장 생성 → `data/images/<bucket>/<id>.png`로 등록.
3. 소품이 **프레임에 보이는 컷**에만 그 시트를 `referenceGallery`(또는 `--reference-gallery-slugs`)에 추가하고, 프롬프트에 `"keep this exact same {소품} design as the reference sheet"`를 명시한다.
4. 소품이 안 보이는 컷(POV·화면 overlay·떡밥 컷 등)은 시트를 넣지 않는다.

프롬프트 구조:

```
Prop reference sheet for {오브젝트명}.
Left half: front view and side view on white background.
Right half: close-up detail panels with annotation callouts showing {질감, 마모, 색상 변화 등}.
{소재, 크기, 시대, 용도}
{특이사항: 벗겨진 칠, 금, 얼룩 등}
Product photography style, hyperrealistic, studio lighting.
```

- `--slug "ref-obj-{오브젝트명}"`, `--quality high`, `--aspect "16:9"`

생성된 시트는 이후 키프레임 생성 시 `--reference-slug` 또는 `--reference-gallery-slugs`로 연결하거나, 프롬프트 앞에 `[연속성 바이블]` 텍스트 블록으로 주입한다.

### Phase 1e: 씬 마스터샷 앵커링 (블로킹·공간 일관성) ★중요

> ★ **레퍼런스 슬롯은 4개가 상한이다 (실측).** 시트를 늘려서 전부 걸 수는 없다. 따라서 "필요한 시트를 다 첨부한다"는 애초에 불가능한 전략이고, **마스터샷 1장이 공간·조명·색보정·블로킹·축선을 한 슬롯에 담는 것**이 유일하게 확장 가능한 방법이다. 결함은 거의 항상 **슬롯이 모자라 뺀 자리**에서 난다 — 컷을 짤 때 "이 컷에서 무엇을 뺐나"를 먼저 적어라.
>
> ⚠️ **cross-category `referenceSlug`는 해석되지 않는다 (실측).** `referenceSlug`/`referenceGallerySlugs`는 **같은 `category` 안에서만** 최신 run을 찾는다. 다른 카테고리의 시트(예: 시트는 `hope-characters`, 컷은 `hope-cuts`)를 걸려면 파일을 해당 버킷(`data/images/<bucket>/`)에 복사하고 **`/api/images/<id>` 전체 URL**을 `referenceGallery`에 직접 넣는다. slug만 적으면 조용히 무시되고, 그 컷만 시트 없이 생성된다.

캐릭터·공간 시트는 **인물 외형과 사무실 생김새**는 고정하지만, **같은 씬 안에서 "누가 어느 자리에 앉아 어느 방향을 보는가(블로킹)"와 "카메라가 어느 쪽에 있나(앵글·축선)"는 고정하지 못한다.** 그래서 시트만 걸면 같은 씬인데도 컷마다 책상 구조·좌석 배치·시선 방향이 새로 그려진다 (실측: 4인 상담 씬에서 컷마다 좌우 배치·카메라 위치가 제각각).

해결: **씬마다 마스터샷 1컷을 먼저 확정하고, 그 이미지를 후속 컷의 reference 1순위로 건다.**

절차:
1. 씬의 **첫 와이드/설정 샷**(인물 배치가 다 보이는 컷)을 먼저 생성하고 베스트 1장을 확정한다 → 이게 그 씬의 "마스터샷".
   - ★★ **마스터가 될 수 있는 컷과 될 수 없는 컷이 있다. 마스터는 "첫 컷"이 아니라 "가장 많이 담은 컷"이다.** 인물의 외형과 상황이 **동시에** 읽히는 **미디엄 와이드**여야 한다 — 너무 넓으면 얼굴이 죽어 캐릭터 앵커 구실을 못 하고, 클로즈업이면 배치·축선이 안 담긴다 (실측 실패: 씬의 첫 컷이 인물 한 명의 작업 클로즈업이라 방어선 배치도 적의 방향도 담기지 않았고, 그 씬 14컷이 컷마다 다른 공간으로 생성됐다 — 절반은 공간 시트조차 안 걸려 있었다).
   - 카메라는 **인물들이 바라보는 방향의 측면 앞쪽**에 둔다. 그래야 인물이 3/4 앞모습으로 잡혀 얼굴이 읽히면서 배치와 적 방향이 함께 프레임에 들어온다.
2. 같은 씬의 후속 컷은 reference를 **`[마스터샷 URL, (그 컷 주연 캐릭터 시트), ...]`** 순서로 구성한다. 마스터샷이 배치·공간·축선을 담당하고, 캐릭터 시트가 클로즈업 시 얼굴 디테일을 보강한다.
   - storyboard spec에서는 후속 cut의 `referenceSlug`/`referenceGallerySlugs`에 마스터 컷 slug를 넣거나, 마스터샷의 `/api/images/<id>`를 `referenceGallery` 맨 앞에 직접 넣는다.
3. 후속 컷 프롬프트 앞에 **블로킹 고정 문구**를 명시한다:
   > "첫 번째 참조 이미지는 이 씬의 마스터 와이드샷이다. 그 마스터샷과 동일한 좌석 배치·책상 구조·공간 레이아웃·카메라 축선을 그대로 유지하라: {좌측 인물}은 왼쪽, {우측 인물}은 오른쪽. 이 배치를 유지한 채 {이 컷의 동작}을 그린다."
4. 클로즈업 컷은 "마스터샷의 {특정 좌석} 인물에게 카메라가 다가간 클로즈업"으로 지시해 좌우 방향(180도 축선)을 깨지 않는다.
5. ★ **좌우 배치(화면축) 규약을 못 박고, 어떤 컷에서도 반전하지 않는다.** 같은 시퀀스에 반복 등장하는 두 인물은 **화면 좌/우 위치를 규약으로 고정**한다(예: "원장 = 항상 화면 왼쪽, 고객 = 항상 오른쪽"). 카메라가 특정 인물을 favor하거나 **리액션·발끈·돌격 같은 동작 컷이어도 좌우를 절대 반전하지 않는다.** 좌우가 뒤집히면 컷 사이에서 인물이 순간이동한 듯 **튀어 보인다**(실측 실패: 평온 투샷은 "원장 왼쪽/고객 오른쪽"인데 바로 다음 발끈 컷에서 "고객 왼쪽/원장 오른쪽"으로 반전돼 축선이 깨짐 → 사용자가 지적). 각 컷 프롬프트에 한국어로 "A는 화면 '왼쪽', B는 화면 '오른쪽', 절대 좌우 반전 금지"를 명시하고, **그 시퀀스의 첫 투샷(또는 마스터샷)을 reference 1순위로** 건다. favor 인물은 샷 크기로 표현하되(예: 오른쪽 인물 미디엄) 좌우 위치 자체는 유지한다.

한계 (정직히): gpt-image 계열은 seed·카메라 좌표 정밀 제어가 없어 **완벽히 동일하진 않다(체감 80~90%)**. 픽셀 단위 동일 배치가 필요하면 동일 베이스 이미지 인페인트나 3D 레이아웃이 필요하며 이 도구 범위를 넘는다. 그래도 마스터샷 앵커링만으로 "같은 씬으로 보이는" 수준은 안정적으로 확보된다 (실측 검증됨).

### 배경 텍스트 고정 (칠판·현판·간판·게시물) ★중요

gpt-image-2는 **글자가 들어갈 표면(칠판·액자·현판·간판·배너·게시물)이 프롬프트에 지정돼 있지 않으면 그럴듯한 한글을 지어내 채운다.** (실측: 반장 선거 씬에서 지시하지 않은 칠판 판서 '오늘의 반장'+임의 후보명이 생성됐고, 칠판 위 국가명 액자('고려민국')가 '고려고등학교'로 둔갑 — 사용자가 발견.) 생성 단계 규칙:

1. **글자 표면이 보이는 컷은 정확한 문구를 한글 그대로 프롬프트에 명시**한다. 쓸 글자가 없으면 "빈 칠판"처럼 비어 있음을 명시한다. 헷갈리기 쉬운 표면은 금지 문구도 함께 명시한다(예: "이 액자는 국가 상징 '고려민국'이다. '○○고등학교' 같은 학교명을 넣지 마라"). gpt-image는 지정한 한글을 정확히 렌더링한다 (실측: 8글자 현판 '황립국민고등학교' 정확).
2. **마스터샷 앵커링은 텍스트 오류도 전파한다.** 어떤 컷을 마스터로 걸기 전에 그 컷의 배경 텍스트부터 검증한다 (실측: 액자가 잘못된 컷을 마스터로 참조한 후속 컷에 같은 오류가 그대로 전이).
3. **고유명은 생성 전에 확정.** 국가명·학교명·기관명이 소스 자료마다 다르면(실측: 설정집 '황제고등학교' vs 시나리오 '황립국민고등학교') 컷 생성 전에 사용자에게 하나로 확정받고 spec에 못 박는다.

### 프롬프트 원리 — 금지보다 조건 ★중요

**"~하지 마라"는 잘 안 듣고 "~인 상태다"는 잘 듣는다.** 부정형은 피해야 할 것만 알려줄 뿐, 대신 무엇을 그릴지는 안 알려준다. 성격이 다른 결함 셋이 전부 같은 전환으로 풀렸다 (실측):

| 결함 | 안 통한 부정형 | 통한 긍정형 조건 |
|---|---|---|
| 군중이 격자로 복제됨 | "복제하지 마라", "같은 자세 반복 금지" | **변주할 축을 6개로 나열** — "간격이 제각각 / 자세가 전부 다름 / 창 각도 제각각 / 앞뒤로 겹침 / 투구 기울기와 갑주 오염도 다름 / 체격과 표정 다름" |
| 간판 한글이 틀림 | "정확히 써라" | 정확한 문구 + **관측된 오답을 실명으로 나열** ("'만나식당'·'무표복덕방'·'대흥서점'이라고 쓰지 말 것") + "글자가 흐릿하게 처리될지언정 틀린 글자를 또렷하게 쓰지 말 것" |
| 개머리판이 어깨에 안 붙음 | "개머리판을 어깨에 밀착시킨다" (3회 실패) | **자세를 바꿔 기하학적으로 강제** — "총열을 차 지붕에 얹고 상체를 낮춘다". 그 자세면 개머리판이 어깨에 들어갈 수밖에 없다 (1회 성공) |

원칙:

1. **금지어를 쓸 거면 구체적 오답을 실명으로 적는다.** 추상적 금지("틀리게 쓰지 마라")는 무효고, 실제로 관측된 오답을 나열하는 것은 유효하다.
2. **결과를 지시하지 말고, 그 결과가 나올 수밖에 없는 조건을 지시한다.** 포즈·견착·시선처럼 반복 실패하는 항목은 지시문을 고치지 말고 **자세·구도·카메라 위치**를 바꿔서 푼다.
3. **3회 이상 같은 지시로 실패하면 지시를 강화하지 말고 조건으로 바꿔라.** 강화는 통하지 않는다 (실측: 견착 지시 3회 강화 전부 실패, 자세 변경 1회로 해결).
4. **가려질 수 있는 부품은 "존재 · 가시성 · 금지"의 3단으로 쓴다.** 형태만 서술하면 모델이 생략을 선택한다.
   - **존재** — "반드시 있어야 한다"
   - **가시성** — 길이 비례·접점·능선 등 **화면에서 무엇이 어떻게 보여야 하는지**
   - **금지** — 관측된 오답을 실명으로

   형태 서술만 있으면 *"그린다면 이런 모양으로"* 로 읽혀서 **아예 안 그려도 위배가 아니다.** (실측: "개머리판은 속이 찬 일자형 검은 플라스틱이고"라고 형태만 썼더니, 견착 자세에서 뺨·어깨에 가려지는 개머리판이 **마스터와 파생 12컷 전부에서 통째로 사라졌다** — 총몸이 사수의 뺨에서 그대로 끝났다. 같은 총을 세워 든 컷에서는 정상이었다. 즉 모델은 **가려지는 구간을 "안 그림"으로 처리한다.**) 개머리판·멜빵·홀스터·손잡이·거치 접점처럼 가려지기 쉬운 부품은 반드시 3단으로 쓴다.
5. **공간 관계는 "가로/세로"가 아니라 "어느 면이 어디를 향하는가"로 지정한다.** 방향 어휘는 화면 기준인지 대상 기준인지 모호하다 (실측: "차량을 사거리에 **가로로** 막고"라고 썼더니 모델이 화면 좌우 기준으로 해석해 차량 긴 축을 화면 가로로 놓았고, 결과적으로 **차 앞머리가 적을 향해 도로가 활짝 열렸다**). 대신 면과 좌표를 함께 준다 — "차량의 **긴 옆면**이 화면 왼쪽(적)을 정면으로 마주한다. 캡은 화면 안쪽 위, 짐칸 뒤는 앞쪽 아래." 한 번에 잡힌다. 차단·엄폐는 여기에 **"사람이 걸어서 통과할 수 있는 열린 통로가 화면 어디에도 없어야 한다"**를 덧붙인다.

### Phase 2: 정리 (index)

batch가 자동 생성하지만, 수동 재생성도 가능:

```bash
node scripts/agent-generate.mjs --build-index moon-running
# → data/agent-runs/_moon-running-index.html
```

index에는 체크박스 + "선택 복사" 버튼이 있어, 사용자가 고른 번호를 채팅에 붙여넣기 가능:

```text
2k로 업스케일: #02, #10
```

### Phase 3: 확정 (업스케일)

사용자가 번호를 주면, 각 `#NN`을 카테고리 index의 run 디렉토리에 매핑 후 업스케일. `--upscale-from`이 manifest에서 revisedPrompt + reference를 자동 추출:

```bash
node scripts/agent-generate.mjs \
  --upscale-from "data/agent-runs/2026-05-16T02-38-05-879Z-attempt-02" \
  --size 2048x1152 \
  --quality high
```

여러 개면 `--batch`로 묶거나 각각 호출. 커스텀 출력명은 `--slug`.

### Phase 1f: 시트 커버리지 정적 검증 (생성 전 필수, 토큰 0) ★중요

키프레임 생성을 시작하기 **전에**, 각 컷이 등장 요소(인물·소품)의 레퍼런스 시트를 빠짐없이 걸었는지 코드로 전수 점검한다. 시트를 만들어도 **그게 보이는 컷에 reference로 안 걸리면 그 컷만 엉뚱한 물건이 나온다** (실측: 가방 시트가 있는데 cut-1-4에만 안 걸어서 갈색 켈리백이 나옴 — 나머지 컷은 정상).

```bash
node scripts/check-coverage.mjs path/to/storyboard.spec.json path/to/coverage-rules.json
```

- `coverage-rules.json`은 `{ "rules": [ { "slug": "pa-obj-bag", "any": ["handbag on the counter", "holding the black beaded handbag", ...], "label": "가방" } ] }` 형태. 각 rule은 "프롬프트/스토리에 any 키워드가 있으면 그 컷은 slug 시트를 reference에 가져야 한다"는 뜻.
- 키워드는 **근접/클로즈업 신호**(들고 있음·카운터 위·핀셋이 닿음 등)로 좁혀라. 단순히 "bag"/"bead"만 쓰면 전경 멀리 있는 컷까지 과탐지된다.
- `ok:false`로 나온 MISS 컷은 생성 전에 spec의 `referenceGallery`에 해당 시트를 추가한다. **이미지가 아니라 spec을 고쳐야** 재생성·재현 시에도 유지된다.

### 안전 필터 대응 — 반복 502 (★중요)

특정 컷이 `--retry`를 줘도 **반복적으로 502 "Codex가 이미지를 반환하지 않았습니다"**로 실패하면, 서버 부하가 아니라 **콘텐츠 안전 필터가 이미지 반환을 거부**하는 신호일 수 있다. 판별 기준:

- **다른 컷은 성공하는데 특정 컷만 3회 이상 연속 502** (일시적 부하라면 재시도 시 분산되어 풀린다).
- 실패 컷의 공통 소재: **미성년자(아동) + 폭력·총기·유혈·공포·위난** 조합. (실측: 제주 4·3 시나리오에서 8세 여동생이 총성·피 흘리는 군중·공포에 노출되는 3개 컷이 동시 502 → 폭력 수위 낮은 17컷은 전부 통과.)

retry로는 절대 안 풀린다. 프롬프트를 단계적으로 완화해 우회한다 (실측: 아래 순서로 3컷 전부 통과):

1. **재현 톤 명시** — 프롬프트 앞에 "역사 다큐멘터리 드라마의 재현 장면" 등을 붙여 기록·재현 맥락을 분명히 한다.
2. **직접적 폭력 표현 간접화** — "총성·피·비명·짓밟힘" 같은 직접 묘사를 빼고 "긴장·보호·충격의 정서"로 바꾼다. (예: "피 흘리는 인파 속 비명" → "황급한 사람들 사이의 긴박한 순간")
3. **군중 패닉·위난 묘사 제거, 인물 중심으로** — 혼란스러운 배경을 단순화하고 보호·유대 같은 정서 중심 구도로 재구성한다. (예: 바닥에 깔려 감싸지는 → 끌어안고 웅크리는)
4. **그래도 막히면 미성년자를 프레임에서 제외** — 주인공(성인/연장자) 단독 컷으로 재구성한다. (예: 트라우마 회상을 "여동생+군중" 대신 "소년 단독 얼굴 클로즈업"으로 → 서사 의미 유지하며 통과.)

완화는 **정서·서사 의미를 보존**하는 선에서 최소한으로. 폭력의 직접 묘사가 빠져도 보호·각성·상실의 감정선은 오히려 더 또렷해지는 경우가 많다.

### Phase 4: 검수 및 맥락 보충

시나리오/스토리보드의 다수 컷 생성 후, 씬 순서대로 리뷰하며 서사 연결을 점검한다. 단일 이미지 탐색에서는 생략.

> ★ **전수 검수 원칙 (표본 금지)**: 생성된 컷은 **표본 몇 개만 보고 "좋다"고 보고하지 말 것.** 반드시 **모든 컷의 썸네일을 Read로 직접 본다.** (실측 실패: 22컷 중 6컷만 보고 통과 보고 → 안 본 17컷 중 2컷에 결함(가방·문서)이 있었고 사용자가 직접 발견함.) 컷이 많아 토큰이 부담되면 사용자에게 "전수 vs 표본"을 먼저 확인하되, 기본은 전수다.

1. **시트 일치 확인** — 각 컷의 인물·소품이 레퍼런스 시트와 같은지 (특히 핵심 소품: 가방·시계·카메라 등). Phase 1f를 통과해도 이미지가 시트와 다를 수 있으니 눈으로 재확인.
2. **검수 Rubric** 기준으로 각 컷 평가 (아래 참조)
3. **문서·간판 텍스트 확인** — 서류/간판이 나오는 컷은 한글 문구가 스토리와 맞는지, 빈 양식이 아닌지 본다 (생성 단계 규칙은 "배경 텍스트 고정" 섹션 참조). ★배경에 **작게** 들어간 액자·간판·판서는 썸네일 수준 검수로는 안 읽힌다 — **해당 영역을 크롭 확대해서 직접 읽는다.** 확대해 읽지 않았으면 "문제 없음"이라고 보고하지 않는다 (실측 실패: 교사 뒤 액자를 확대 안 하고 '학교명 오류 없음'으로 오보고 → 사용자가 '고려고등학교' 오기를 발견).
4. **서사 연결 점검** — 다음 유형의 누락을 찾는다:
   - 씬 오프닝에 에스터블리싱/와이드 샷이 없는 경우
   - 컷 간 감정·시각 전환이 급격해 브릿지 컷이 필요한 구간
   - 주요 인물이 여러 컷 동안 사라지는 구간 (리액션 컷 누락)
   - 씬 전환 시 시간 경과·공간 이동을 시각적으로 보여주는 전환 컷 부재
5. **보충 컷 제안**: 누락을 사용자에게 보고하고 확인 후 추가 생성한다.
6. **외부 모델 교차 검증** (컷이 많을수록 효과가 크다). 컷이 수십 장을 넘으면 본인 컨텍스트로 전수 검수가 물리적으로 불가능하다. Codex 등 별도 세션에 **읽기 전용 자문**으로 전수 스캔을 맡기면 그 한계를 넘길 수 있다 (실측: 92컷 스캔 1회로 35건 지목).
   - **자기가 쓴 문서의 산술·연속성 오류는 저자가 못 본다.** 외부 검증이 가장 크게 이기는 지점이 여기다 (실측: 탄약 잔탄 계산 모순, 소품을 떨어뜨린 장소와 주운 장소 불일치 — 본인이 여러 번 읽어도 못 찾았음).
   - **판정을 그대로 믿지 마라. 실측 채택률 약 60%.** 나머지는 오탐이거나 과대평가였다 (실측: 실물 M16A1 총열덮개가 측면에서 리브 구조로 보이는 것을 "심각도 상" 결함으로 13컷에 지목 → 그대로 따랐으면 13컷 헛 재생성). **모든 지적은 근거를 대조한 뒤 채택/기각을 명시적으로 판정**하고, 기각 사유를 남긴다.
   - 반대로 **사용자 지적을 외부 검증이 기각하는 경우도 있다.** 이때도 본인이 독립 확인한다 (실측: 시트 좌우 반전 의심을 기각해 파생 컷 연쇄 재생성을 막음).
7. **채택 목록과 실제 재생성 spec을 코드로 대조한다.** 지적을 "채택"으로 판정해놓고 배치 spec에 안 넣으면 그대로 누락되고, 최종 보고가 틀린다 (실측: 채택 1건이 배치 A·B·C 어디에도 안 들어갔는데 "남은 건 P2뿐"이라고 보고함 — 사용자가 재확인 요청해서 발견).

   ```bash
   # spec에 실제로 들어간 slug
   grep -ho '"slug": *"[^"]*"' batch*.spec.json p0-fix.spec.json \
     | sed 's/.*: *"//;s/"$//' | sort -u > /tmp/regenerated.txt
   # 채택 목록(accepted.txt)과 비교 — 왼쪽에만 있으면 누락
   comm -23 <(sort -u accepted.txt) /tmp/regenerated.txt
   ```


8. **전술·지형 기하** (방어선·바리케이드·엄폐·매복·차단이 나오는 컷). 축선(적이 어느 쪽인가)이 맞아도 **배치가 성립하지 않을 수 있다.** 다음을 따로 본다:
   - 차단물이 실제로 통로를 막는가, **우회 가능한 공간이 열려 있지 않은가**
   - 엄폐물이 방어자와 적 **사이**에 있는가 (방어자 뒤편에 쌓인 짐이 아닌가)
   - 사선에 **자기편 구조물**(차체·기둥·동료)이 걸리지 않는가
   - 각 인물이 실제로 엄폐를 받는가, 상체를 통째로 내놓고 있지 않은가

   (실측 실패: 축선은 정확했으나 차단 차량이 도로와 평행해 통로가 열려 있었고, 엄폐물이 방어자 쪽에 흩어져 있었으며, 노인이 노출된 위치에 있었다. **검수자는 통과시켰고 사용자가 발견했다.** 이 항목이 체크리스트에 없었기 때문이다.)
9. **무기는 앞뒤를 나눠 본다.** 앞쪽 특징(운반손잡이·총열덮개·탄창·소염기)이 정확하면 전체가 정확하다고 판정하기 쉽다. **개머리판·멜빵처럼 인물에 가려지는 뒤쪽은 별도 항목으로 확인한다** (실측: 12컷 전수 검수를 하고도 개머리판 부재를 놓쳤다 — 앞쪽만 보고 "M16A1 정확"으로 판정했다).

보충 컷의 slug는 `cut-{씬}-{번호}b`로 구분한다.

## 캐릭터 라이브러리 (재사용 캐릭터)

웹 UI `/studio/characters`에서 캐릭터를 등록(name + handle)하면, 단일 생성 prompt에서 `@handle`로 호출 가능:

- **등록**: 프리셋 시트 결과 / 히스토리 / 단일 생성 결과의 "캐릭터로 등록" 버튼 (copy-on-import로 원본 보호)
- **사용**: 단일 생성 prompt에 `@민수가 카페에 들어선다` → 매칭된 캐릭터 이미지가 참조 슬롯에 자동 첨부 + Reference map prompt 자동 합성
- **picker**: "캐릭터 라이브러리에서" 버튼 → 검색/태그 필터 모달

helper(CLI)에서 캐릭터를 쓰려면 해당 이미지 URL(`/api/images/<id>`)을 `--reference`로 전달.
이전 helper run을 참조할 때는 URL을 직접 복사하지 않고 slug로도 지정 가능:

```bash
node scripts/agent-generate.mjs \
  --prompt "cut-03 prompt" \
  --category "storyboard-demo" \
  --slug "cut-03" \
  --reference-slug "cut-02" \
  --reference-gallery-slugs "character-base,prop-base"
```

`--reference-slug`는 같은 category 안에서 `manifest.slug`와 run 디렉토리 suffix가 일치하는 최신 run의 첫 `/api/images/<id>`를 사용. `--reference`를 직접 주면 직접 URL이 우선.

## 검수 Rubric (Medium)

생성 후 `Read` tool로 이미지를 직접 보고 평가:

- `subject`: 인물/주체가 프롬프트 의도와 일치
- `background`: 배경/환경이 장면 조건과 충돌 없음
- `pose`: 자세/동작 명확, 왜곡 없음
- `style`: 시각 스타일·색감·조명·렌더링 톤 일치
- `missing`: prompt 핵심 요소 누락 여부
- `notes`: 손/얼굴/텍스트/로고/프레이밍 특이사항

명백한 누락이면 최대 1회 자동 재생성 후 사용자에게 비교 보고 (semi-auto).

## Limits

- 단건 생성 60~120초. **`--batch --concurrency`로 병렬 가능** (concurrency 4 권장 안전선).
- Codex rate limit (사용자 ChatGPT Pro 쿼터) — 동시 과다 시 일부 429 실패 가능.
- **딜리버리 스토리보드는 2K(`2048x1152`) 기본.** 빠른 탐색은 `1824x1024`로 싸게 뽑고 베스트만 `--upscale-from`으로 2K 확정하는 흐름도 가능. 단, 사용자가 최종본을 기대하면 처음부터 2K로 생성한다.
- 2K 업스케일은 1K와 픽셀 동일하지 않음. 구도·색감 90%+ 유지 수준.
- 반복 등장 소품은 오브젝트 시트로 외형 고정 (Phase 1d 참조). 추상 표현만 쓰면 컷마다 다른 물건이 나옴.
- 이미지는 로컬 디스크 저장. 생성 시 prompt 사이드카(`{id}.json`)도 저장돼 디스크에서 복원해도 prompt 유지.

## 실전 교훈 — 대규모 사극 전투 스토리보드 (진주성 세션, 반드시 적용)

이 9가지는 실제로 큰 손실(전면 재작업·전량 폐기)을 낸 함정들이다. 새 작업 시작 전에 점검한다.

1. **에셋 폴더는 하위까지 전수 조사 후 시작.** 최상위만 보고 시작하면 안 됨. (병종별 군복이 든 하위 폴더를 놓쳐 군복을 임의로 잡았다가 조선군 전 컷 재작업.) 빈 폴더(배경/오브젝트 시트)면 앵커를 직접 생성해야 함을 즉시 인지.

2. **사용자 시트가 정본. 시나리오 바이블 텍스트와 충돌하면 시트 우선** (또는 어느 쪽 따를지 사용자에게 1회 확인). 참조하는 **모든 시트를 시작 전 육안 확인** — 안 보고 텍스트만 믿으면 황진(적금 vs 흑갈색)·김천일(검은수염 vs 흰수염) 같은 충돌을 놓친다.

3. **앵커 시트도 실사 시네마틱 톤으로.** "균일 조명·중립 회색 배경"으로 뽑으면 게임 에셋 턴테이블 톤이 되고 그게 컷에 전이됨. "실사 영화 의상 레퍼런스, 자연 시네마틱 측광, 35mm 필름, 3D 게임 렌더·CGI 아님"을 명시. 가능하면 사용자 실사 시트를 직접 등록해 쓴다.

4. **대군은 그릴 수 있다 (gpt-image-2).** "못 그린다" 단정 금지. 패턴: **항공 부감 익스트림 와이드 + 사각 방진(블록) 단위 편성 + 지평선까지 원근 축소 + 수백 깃발 + 층층 먼지.** 수만 규모 체감 가능.

5. **공간 일관성 = 마스터-샷 앵커 (Phase 1e를 같은 장소 다컷 씬 전체에 적용).** 같은 장소의 establishing 1컷을 먼저 확정 → 나머지 컷을 그 **생성된 이미지 id**를 `referenceGallery` 1순위로 걸어 생성. 컷마다 독립 생성하면 같은 장소가 매번 다른 곳이 된다.

6. **전장 지리 규약을 좌표로 못 박는다.** (예: 들판/밖=화면 왼쪽, 성벽=오른쪽/전방, 공격은 좌→우.) 각 컷 프롬프트에 화면상 위치(좌하/중하/우상 등)와 시선·진격 방향을 명시해야 컷 간 방향·블로킹이 일관됨.

7. **검수는 적대적으로.** "완벽/압권" 같은 자기확신 금지. 흠을 먼저 찾는다: 모든 재등장 인물을 전 컷 교차 비교, 규모·진격방향·공간일관성·화풍·개연성(예: 지휘관 옆 호위 유무, 저격수 은폐 여부)까지. 확증편향이 가장 큰 적.

8. **장시간 배치 운용.** ① 생성 타임아웃은 2K+다중레퍼 기준 **180초로 부족 → 480초**(`SIONBANANA_GEN_TIMEOUT_MS`). ② 서버는 **독립 호스팅**(런처 Terminal)으로 — 에이전트 백그라운드 자식으로 띄우면 작업 리핑 시 같이 죽음. ③ **타임아웃돼도 서버는 이미지를 저장**함 → 재실행 전 기존본을 프롬프트 매칭으로 재사용(중복 생성 방지). ④ 청크 run이 `index.html`을 덮으므로 통합 index는 별도 1회 생성.

9. **이미지 검수 한도.** 1장당 ≤2000px. 한 세션에 이미지가 과다 누적되면 더 이상 못 봄 → 검수는 핵심만 분할해서, 필요하면 새 세션으로 리셋.

## 실전 교훈 — 지시 불이행 교정과 액션 인서트 (호포 세션, 반드시 적용)

앞 절이 "무엇을 그릴지"의 함정이라면, 이 3가지는 **"지시했는데 안 그려질 때"**의 함정이다. 같은 컷을 3번 넘게 돌리게 되는 원인이 대부분 여기 있다.

### 10. 결과가 아니라 물리를 써라 — 모델은 상태를 못 지키고 배치를 지킨다

**"뺨이 개머리판에 붙어 있다"는 두 번 무시됐고, 아래 문구는 한 번에 통했다:**

> `★총몸이 화면을 사선으로 가로질러 ★그녀의 턱 바로 아래를 지나간다.`
> `★개머리판 끝이 오른쪽 쇄골 아래 어깨의 우묵한 자리에 깊이 파묻혀 셔츠 천이 접히고 어깨살이 눌려 들어갔다.`
> `★그녀의 오른눈이 총 위 조준선 높이에 정확히 놓였다.`

차이는 **검증 가능성**이다. "붙어 있다"는 그려놓고 나서야 판정되는 결과지만, "화면을 가로질러 턱 아래를 지난다"는 **화면상 배치**라 그리는 도중에 결정된다. "어깨살이 눌려 들어갔다"는 **접촉의 물리적 흔적**이라 접촉 없이는 그릴 수 없다.

**규칙:** 자세·접촉·지지가 중요한 컷은 세 가지로 쪼개 쓴다.
1. **화면상 배치** — 무엇이 화면 어디를 가로지르는가
2. **접촉의 흔적** — 눌린 천, 접힌 살, 파인 자국
3. **기하 구속** — 눈높이 = 조준선 높이, 팔꿈치가 몸통 아래로 곧게

결과만 쓴 문장(`~한 상태다`, `~하고 있다`)은 첫 실패 후 재사용하지 마라. 같은 방식으로 또 실패한다.

### 11. 3회 실패하면 고치지 말고 프레임에서 빼라

한 컷을 3회 돌렸는데 **매번 다른 곳이 어긋나면**, 그건 프롬프트가 부족한 게 아니라 **프레임에 요소가 많은 것**이다.

실측: 어떤 컷이 1차에 조연의 무기, 2차에 주인공 자세, 3차에 조연의 소지품이 어긋났다. 세 결함의 공통점은 **조연이 프레임에 있다는 것**뿐이었다. 조연을 빼자 4차에 한 번에 통과했다.

**판정 기준 — 아래를 만족하면 빼는 것이 정답이다:**
- 그 인물·사물이 **이 컷의 정보를 나르지 않는다** (앞뒤 컷에 이미 나온다)
- 뺀다고 **연속성이 깨지지 않는다** (같은 공간에 있다는 사실은 앞 컷이 이미 증명했다)

빼는 지시는 **가능한 위치를 전부 부정**해야 한다. `등장인물은 한 명뿐이다`만으로는 부족하다:

> `★★[등장인물 — 단 한 명] ★이 컷에 사람은 A 한 명뿐이다. ★B는 프레임 안에 없다.`
> `★차 안에도, 차 뒤에도, 화면 가장자리에도 두 번째 사람을 그리지 말 것.`

### 12. 인서트의 다양성은 앵글이 아니라 피사체로 만든다

같은 사건의 인서트 5장을 **카메라 각도만 바꿔** 설계하면 "비슷비슷하다"는 평가를 받는다. 미디엄·클로즈업·와이드는 전부 *같은 것을 다른 거리에서* 본 그림이기 때문이다.

**컷마다 피사체 자체를 바꾼다.** 한 사건에서 뽑을 수 있는 축:

| 축 | 무엇을 찍는가 | 예 |
|---|---|---|
| 도구 | 행위의 수단 | 전경에 무기를 크게 건 OTS |
| 신체 | 행위자의 일부 | 발사 순간의 두 눈 — 동공에 화염이 점으로 |
| 기계 | 도구의 작동부 | 실린더가 한 칸 회전하는 ECU |
| 대상 | 행위를 당하는 쪽 | 쓰러지는 적 — 촬영자가 화면에 없다 |
| 규모 | 행위의 무의미함 | 부감 — 주인공은 구석의 점, 화면은 적이 채운다 |

**대상 축에서는 "각기 다르게"를 자세 목록으로 못 박는다.** `셋이 다르게 쓰러진다`만 쓰면 군무가 나온다. 셋을 각각 **정지 자세 하나씩**으로 지정하고, 연속 동작(`무릎이 접혀 → 고꾸라지고 → 손을 짚고`)은 한 프레임에 겹치므로 금지한다.

> `① 상체가 뒤로 젖혀졌으나 두 발은 아직 땅에 붙어 있다. 놓친 창이 머리 위 공중에 떠 있다.`
> `② 이미 엎어져 두 손바닥과 두 무릎이 땅에 닿은 채 멈춰 있다. 벗겨진 삿갓이 바로 앞에 뒤집혀 놓였다.`
> `③ 몸 전체가 공중에 떠 옆으로 비틀린 채 어깨가 지면에 닿기 직전이다. 두 다리가 완전히 떠 있다.`

## 생성 파이프라인 — 순서와 게이트 (호포 씬2 사태 이후 확정)

앞의 교훈들이 "프롬프트를 어떻게 쓰나"라면 이 절은 **"어떤 순서로 돌리나"**다. 씬 2에서 31컷 중 30컷이 결함으로 나온 원인은 프롬프트가 아니라 이 순서를 건너뛴 것이었다.

```
① 자산 대장 확인 → ② 프롬프트 교차검증(시트 첨부) → ③ ★키프레임 확인 게이트
→ ④ 파일럿 1컷 → ⑤ 배치 확장 → ⑥ Codex 자율 검수 → ⑦ 지적분만 재생성
```

### ① 자산 대장 — 시트가 정본이다. 산문을 다시 쓰지 마라

작업 전에 **그 씬이 쓰는 시트를 실제로 연다.** 각 시트가 무엇을 고정하는지 한 줄씩 적고, 이후 모든 프롬프트와 검수 규약은 **그 대장에서만** 나온다.

**실패 사례 (호포 씬2):** 세계관을 CONTINUITY 텍스트에서 산문으로 옮겨 적어 썼다. 결과:
- "왜군 갑주는 갈색" ← 실제 시트는 **천만 갈색, 금속 갑주는 검정.** 이 잘못된 전제로 검수 오판 9건이 생겼다.
- 순찰차 시트(`obj-01`)가 있는 줄 모르고 "없다"고 단정 → **31컷 중 0컷이 참조.** 푸시바·문장 위치·앞뒤 표기가 컷마다 달라졌다.

★ 시트가 정하지 않는 것(예: 번호판, 간판의 좌우 배치)은 **씬이 정해야 하는 것**이다. 추론으로 규약을 만들지 말고 명시적으로 결정해 문서에 남긴다.

### ② 교차검증에 시트를 **이미지로** 첨부한다

`codex exec -i <파일>...` 는 이미지를 여러 장 받는다. 프롬프트 텍스트만 주고 검수시키면 **내 산문이 틀린 만큼 검수도 같이 틀린다.** 컷과 관련 시트를 함께 붙여 그림 대 그림으로 대조시켜라.

주의 — `-i`는 가변 인자라 뒤에 오는 프롬프트 문자열을 삼킨다. **프롬프트는 stdin으로 넘겨라.**
```bash
cat prompt.txt | codex exec --sandbox read-only -c model_reasoning_effort='"high"' -i a.png -i b.png
```
이미지 6장 이상이면 websocket이 자주 끊긴다. **3장씩 쪼개고 재시도 루프를 걸어라.**

### ③ ★키프레임 확인 게이트 — 여기를 건너뛰면 전부 오염된다

**파생 배치를 돌리기 전에 마스터를 눈으로 열어 통과 판정한다. 기존 마스터를 재사용할 때도 예외 없다.**

**실패 사례:** `master-s2b`를 15컷의 1번 슬롯에 걸고 파생시켰는데, 그 마스터를 한 번도 열어보지 않았다. 마스터에는 **두 경찰이 권총을 겨눈 상태**가 박혀 있었고, 프롬프트에 인물 상태를 안 쓴 컷이 전부 그 자세를 물려받았다. 확인 1회면 15컷이 안 오염됐다.

**마스터의 자격 — 공간 마스터로 만들어라.**
- ★사람·차량을 넣지 마라. 마스터에 든 인물은 파생 컷에 **상태까지 그대로** 전파된다.
- 공간·간판 배치·색보정·카메라 방향만 담는다. 인물과 차량은 각 컷이 자기 시트로 책임진다.
- 간판의 좌우 순서가 **카메라 방향의 지표**다. 방향 축이 고정이면 간판 순서도 고정이어야 한다.

### ④ 파일럿 1컷 — 배치 전에 가장 어려운 컷 하나만

확정될 때까지 그 컷만 고친 뒤, 확정된 프롬프트 골격을 나머지에 복제한다.

**실측:** 파일럿 없이 15컷을 한 번에 돌려 **27회 호출(재작업 1.80배)**, 그러고도 통과율이 사실상 0이었다. 반면 마스터 3종은 복잡도 예산을 걸고 뽑아 1차에 체계 문제 6개가 전부 해결됐고 재작업 사유는 결함이 아니라 구도였다.

### ⑤ 프레임 복잡도 예산 ≤ 3 — ★를 더 붙이지 말고 프레임에서 빼라

**한 프레임이 독립적으로 맞춰야 할 것이 셋을 넘으면 컷을 쪼개거나 요소를 뺀다.**

★ 밀도와 결함 수의 상관은 **r = 0.17로 거의 없다.** 양 극단이 다 실패한다. 실제 예측 변수는 규칙 수가 아니라 **프레임이 저글링하는 항목 수**다.

| 컷 | 맞춰야 할 것 | ★ | 결함 |
|---|---|---|---|
| `07b` 눈 ECU | **1개** (두 눈) | 18 | **0** |
| `12c` 무릎쏴 | **6개** (자세·화염위치·적 반응·조연·다리·흙먼지) | 36 | **20** |

넷째 항목이 생기면 그것은 **다음 컷의 소재**다.

### ⑥ 슬롯은 "글로 대체 안 되는 것"에만 준다

실측으로 갈린다:
- **글로 대체된다:** 장소·배경·조명 (산문 묘사로 충분히 재현됨)
- **글로 대체 안 된다:** 총기 형태, 차량(문장 위치·부착물·앞뒤 표기), 인물 얼굴

슬롯 4칸에 "대체 불가" 항목이 다 안 들어가면 **그건 복잡도 초과 신호**다. ⑤로 돌아가 요소를 빼라.

### ⑦ 검수 분업 — 전수 육안을 하지 마라

**Codex 1차(자율) → 지적분만 내가 확대해 확정/기각.**

★ Codex에 체크리스트를 주지 마라. 세계관과 각 컷의 연출 의도만 주고 **"이 컷이 실제 영화에 들어갈 수 있는가"**로 열어라. 예시를 줄 때도 "목록이 아니다"를 명시하고, 애매하면 침묵하지 말고 '추정'으로 적게 하라.

**실측 (같은 31컷):**

| | 체크리스트 방식 | 자율 방식 |
|---|---|---|
| 지적 | 약 40건 | **274건** |
| 결함 컷 | 18/31 | **30/31** |

체크리스트로는 **사선 안전**(총구 연장선에 아군), **총기 조작 논리**(M16 방아쇠로 유탄 발사), **투사체 방향**(화살·창이 역방향으로 박힘), **손상 누적**(앞유리 균열이 사라졌다 나타남), **부품 부재**(개머리판 통째로 없음)를 한 건도 못 잡았다. 규칙에 없었기 때문이다.

**내 전수 육안은 신뢰하지 마라.** 같은 세션에서 체크리스트로 6컷을 "통과"시켰고 자율 검수는 그중 5컷에서 치명 결함을 찾았다. 반대로 Codex 지적분을 확대 검증했을 때는 **10건 중 9건 적중**이었다. 인간(에이전트) 쪽은 **판정에만** 쓰는 것이 정확도·비용 모두 낫다.

## 파이프라인 실전 적용에서 나온 보정 (호포 씬2 재건·썸네일 세션)

앞 절의 파이프라인을 실제로 돌리면서 드러난 단서들이다. **특히 ⑤복잡도 예산과 ⑥슬롯은 아래 단서 없이 적용하면 새로운 결함을 만든다.**

### 13. ★그 컷에서 가장 큰 피사체는 무조건 슬롯을 갖는다

복잡도 예산을 지킨다고 **슬롯을 아끼면 안 된다.** 실측 두 건:

| 컷 | 슬롯 구성 | 결과 |
|---|---|---|
| 총 근접 (손이 프레임의 절반) | 무기 + 마스터 + **왜군** — 윤서진 시트 없음 | 유일한 인물 참조인 **왜군의 갈색 소매가 손에 전파**됐다. 주인공의 총을 적이 쥔 그림 |
| 탄피 클로즈업 (탄피가 주 피사체) | 무기 시트로 갈음 | 무기 시트가 고정하는 탄약은 **40mm 유탄뿐**이라 5.56mm 탄피 자리에 **유탄 약협**이 나왔다 |

**둘 다 "이 컷엔 손만 나오니까", "탄피만 나오니까" 하고 슬롯을 줄여서 생긴 것이다.**

**규칙:** 프레임에서 큰 면적을 차지하는 것은 그것이 신체 일부든 소품이든 **전용 시트를 슬롯에 넣는다.** 넣을 자리가 없으면 그건 복잡도 초과 신호이지 슬롯을 아낄 이유가 아니다.

★ 무기 시트가 그 무기의 **모든 탄약**을 고정한다고 가정하지 마라. 시트에 실제로 무엇이 찍혀 있는지 확인하라(§자산 대장).

### 14. 복잡도 예산으로 뺄 수 있는 것은 장식이지 전제가 아니다

씬 2는 "차문이 방패이자 총열 거치대"라는 전술적 전제 위에 있다. 복잡도를 줄인다고 순찰차를 프레임에서 빼자, 주인공이 **대군 앞 빈 도로에 엄폐물 없이 혼자 서 있는** 그림이 됐다. 앞 컷은 차문 뒤, 뒤 컷도 차 옆인데 그 사이 다섯 컷만 도로 한복판 — **순간이동**이다.

**뺄 후보를 고를 때 자문한다:** 이것이 없으면 *그림이 단순해지는가*(장식), 아니면 *상황이 성립하지 않는가*(전제). 전제는 빼지 말고 **다른 것을 빼라.**

### 16. ★검수에 "부재" 질문을 따로 넣어라 — 쓰인 것만 보면 부재는 영원히 안 보인다

같은 31컷에 대해 **프롬프트 텍스트 검수는 10건, 이미지 검수는 274건**을 찾았다. 차이의 정체는 이것이다 — **이미지에서는 부재가 보이지만("개머리판이 없다"), 텍스트에서는 안 보인다.** 안 쓰인 문장은 읽을 수가 없다.

그래서 검수 요청에 **(A) 있는 것의 결함**과 별도로 **(B) 부재**를 명시적으로 물어라:

> **(B) 있어야 하는데 없는 것**
> - 이 컷에 반드시 있어야 하는데 **프롬프트에 한 줄도 안 적힌 것**은 무엇인가
> - **슬롯 4칸 배정이 틀린 곳** — 형태가 중요한데 슬롯에 없는 참조, 반대로 슬롯을 차지했지만 화면에서 작아 글로 대체 가능했던 참조
> - STORY가 요구하는데 이 배치가 통째로 빠뜨린 요소
> - 앞뒤 컷에는 있는데 이 컷에서 사라진 것

그리고 검수자에게 **결과 이미지만 주지 말고 그 이미지를 만든 입력 전체(슬롯 파일명 목록 + 마스터 이미지)**를 함께 줘라. 슬롯 목록이 없으면 "차 시트가 슬롯에 없다"를 판정할 방법이 없다.

★ **내 산문 요약을 검수 입력으로 주지 마라.** 요약이 틀리면 그 오류가 "독립 검증"의 외피를 쓰고 돌아온다. 실측: 세계관을 산문으로 옮겨 적어 준 결과 **274건 중 14건이 내가 지어낸 전제로 생긴 오판**이었고, 그중 「검은 가죽 점퍼」는 **어느 문서에도 없는 내가 만든 말**이었다(시트는 감청색 항공점퍼). 원문 경로와 시트 이미지를 주고 직접 읽게 하라.

### 17. 방향은 화면 좌표가 아니라 프레임 안의 표적으로 결정한다

인물을 뺀 공간 마스터에는 **적이 어디 있는지가 없다.** 그 상태에서 `★총구는 화면 왼쪽을 향한다`고 써도 걸릴 데가 없어 반대로 나온다.

**표적을 프레임 안에 넣으면 한 번에 잡힌다:**

> `★화면 왼쪽 원경에 왜군 대열이 야리를 낮추고 달려온다.`
> `★윤서진은 화면 오른쪽에 서서 그 대열을 향해 쏜다 — 총구와 화염과 시선이 모두 화면 왼쪽을 향한다.`

★ 공간 마스터에서 인물을 빼는 것은 오염을 막지만 **방향 정보도 같이 사라진다**는 것을 기억하라. 간판 순서는 카메라 방향의 지표가 되지만 **적의 방향은 담지 못한다.**

### 18. 물리는 "그 화각에서 실제로 보이는 것"으로 써라

§10(결과가 아니라 물리)의 보정이다. **물리적 서술이라도 그 화각에서 화면상 작으면 무시된다.**

견착이 클로즈업에서는 잡혔는데 **전신 로우앵글에서는 세 번 실패**했다. 어깨-뺨 접점이 전신 프레임에서 너무 작기 때문이다. 실루엣에서 크게 보이는 것으로 바꾸자 한 번에 통과했다:

> `★오른 팔꿈치가 어깨 높이까지 들려 옆으로 벌어진다. ★왼 팔꿈치는 총 아래로 곧게 내려와 몸통에 가깝다.`

견착한 사수와 총을 뻗어 든 사람은 **팔꿈치 높이가 다르고**, 그 차이는 전신 실루엣에서 읽힌다. **화각을 정한 다음, 그 화각에서 판별 가능한 물리 지표를 골라라.**

### 19. 참조 이미지의 상태가 프롬프트 문장을 이긴다

베이스 이미지를 1번 슬롯에 걸고 `구도와 인물 배치를 계승하라`고 하면, **베이스에 찍힌 인물의 상태(착용물·자세·소지품)까지 계승된다.** 문장으로 반대를 지시해도 진다.

실측: 썬글라스를 손에 쥐게 하는 지시가 **3회 연속 실패**했다. 베이스에 착용 상태가 박혀 있었기 때문이다. 마스터에 박힌 권총 자세가 15컷에 전파된 것과 **같은 구조**다.

**베이스를 참조로 쓸 때는 "베이스와 달라야 하는 점"을 명시적으로 대비시켜라:**

> `★베이스 이미지에서 그가 썬글라스를 쓰고 있더라도, 이 컷에서는 벗어서 손에 쥔다.`
